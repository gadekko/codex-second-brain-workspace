# Updates, corrections and validation

## Update the existing authority structure

Identify the supplied material and compare it with current records. Preserve unrelated edits, original inputs and prior decisions. Decide whether each change is an accepted requirement, a proposal, a sourced fact, a correction, a duplicate or an unresolved conflict.

Maintain enough provenance to reconstruct what was known and chosen at the time. A later outcome does not retroactively change the original decision's information set. Supersede an old instruction only when the user's current direction or applicable authority supports it; a newer source timestamp alone is insufficient.

Follow dependencies: if a requirement changes, inspect the plan, acceptance criteria, task board, current status and active deliverables it affects. For sources, identify the claims that relied on the superseded version. Record unresolved dependents as stale with a next action. Historical handoffs should remain historical; append a correction rather than rewriting what was observed then.

Avoid repeat intake of unchanged covered material. Preserve new occurrence context even if its bytes match something already read. Check for in-scope arrivals during a substantial build; reconcile the opening and closing snapshots. If time or access prevents full processing, leave a truthful incomplete state rather than reducing the denominator.

## Interrupted work

Save what was actually processed, exact pending source/ranges, failed operations, affected stale records and the next command/action. On resume, check changed source bytes and current files before reusing a prior completion flag. A saved queue does not execute itself; an automation needs real scheduling and applicable user authorization.

One integrator owns canonical state during delegated work. Workers get bounded inputs and exclusive outputs; returned findings include provenance and coverage. Reconcile current files before applying worker output. Independent tasks and separate checkouts do not share locks or histories automatically.

## Observable acceptance

Scale checks to risk. After a small requirement edit, inspect the affected views and local links. After a new helper, run meaningful behavioral tests. After substantial restructuring, have a reader without the old conversation recover:

- The project purpose, actual constraints and accepted versus proposed choices.
- What exists and was tested, supported by an exact local record or source locator.
- A material uncertainty or contradiction and its practical consequence.
- The next action and any real access/input dependency.
- Where to make a bounded update without creating competing current records.

Useful forward tests use wholly synthetic material in an isolated workspace: an existing combined-document project, a later changed requirement, a conflicting source, an interrupted read or a broken preservation hash. Give the evaluator the skill, realistic request and minimum raw inputs. Do not supply the intended answer or disguise real client material by renaming it.

Review the actual result, including changes outside the intended files. Preserve originals, accepted scope and unaffected work; apply concrete corrections and recheck affected behavior. A structural pass or a model saying the skill looks good is not a semantic test.

## Distribution and completion claims

For a reusable skill, package only method files, required helper resources and synthetic tests. Inspect exact contents and unresolved absolute paths before installation or sharing. Keep project evidence, credentials and client facts outside the distribution.

Validate names/frontmatter with the available skill validator when authoring for Codex. Run helper tests and an actual isolated usage test when warranted. Then distinguish filesystem installation from automatic skill discovery: do not claim that a current client has loaded it unless observed.

Finish the requested endpoint. Describe coverage and remaining access/substantive uncertainty without claiming that a scaffold or sampled corpus is a completed knowledge base. No hosting, remote backup, connector, paid service, external transmission or always-running memory process follows automatically from a local build.
