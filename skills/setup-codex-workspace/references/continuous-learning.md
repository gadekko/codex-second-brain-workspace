# Operate the workspace and improve it over time

The objective is a working environment in which Codex can handle the person's authorized work across connected tools, using current knowledge and learning from actual results. Improvement means maintaining source-linked context, confirmed preferences, workflow methods and tested skills. It does not mean retraining the model, magically inheriting every conversation or promising unrestricted access to every tool.

## 1. Establish the private operating home

Choose the user's private folder or private repository and record its actual storage/access boundary. It is expected to contain real authorized work: documents, correspondence or references to it, project knowledge, profiles, task links, generated skills, run receipts and corrections. Do not confuse this with the toolkit source repository, which must contain generic methods only. A method copy can live inside the private workspace, with private state in clearly mapped neighboring directories excluded from any generic toolkit export.

Map responsibilities to existing records rather than imposing duplicate files:

| Record | Purpose |
| --- | --- |
| Workspace entrypoint and project map | Projects, responsibilities, current context routes and confidentiality boundaries |
| Source/coverage map | Accounts, folders, history windows, originals, versions, reviewed scope, gaps and refresh checkpoints |
| Workflow/capability map | Jobs the person wants handled, tools/accounts needed, tested capabilities, allowed actions and missing dependencies |
| Profiles and decisions | Confirmed voice/preferences, dated decisions, evidence, uncertainty and supersession |
| Skill register | Actual skill locations, versions, dependencies, authority, install/discovery and test states |
| Correction and learning ledger | Specific observation, source or feedback, scope, affected records, action taken and validation |
| Runtime and recovery records | Scheduler IDs, checkpoints, duplicate keys, failures, rollback and next action |

The person's familiar task manager remains authoritative for human tasks when selected. Link its real IDs and verified state. Keep distinct projects/clients compartmentalized while a top-level map routes requests to authorized context. A cross-project index is not permission to disclose one project's information in another.

## 2. Install a daily-work contract

Merge these obligations into the private workspace's governing startup/maintenance instructions using real paths:

1. At task start, resolve the relevant project, current instructions, active corrections, source coverage and the appropriate skills. Refresh volatile facts when necessary. Retrieve the source detail required for the task rather than loading every historical file or trusting an old summary.
2. Identify required tools, correct accounts, allowed actions and completion criteria. Use the existing capability map; if something is missing, help connect/test it or state the exact gap. Do not substitute an unrelated account.
3. Perform the authorized work across the actual tools and verify the result in the destination system. Where authority covers sending, updating tasks or other actions, complete that scope; where it does not, prepare the reviewable result for the user's decision.
4. At task close, update the authoritative knowledge and affected views, persist the real output/status, retain source locators and unresolved work, and record corrections or demonstrated workflow failures. Preserve sent/filed originals and historical states.
5. Apply warranted private skill/profile improvements under the agreed maintenance scope, test them and record the revision. Do not claim a lesson was learned merely because it was mentioned in chat.

These records provide durable context across tasks. They do not themselves guarantee native assistant-memory recall or scheduled execution. Global/native memory writes follow the environment's separate rules, including any explicit-request requirement.

## 3. Turn experience into a bounded improvement

Recognize different kinds of change:

- **Explicit user correction:** record the actual correction, context and effective date. Propagate it to current knowledge, profile and affected skill instructions. Do not generalize a request for one recipient into a universal writing rule.
- **New evidence:** preserve the source/version, review it and reconcile affected claims. Conflicting evidence creates an unresolved issue unless there is a justified supersession.
- **Observed successful/failed behavior:** keep the actual task, tool result and output. A failure can reveal a bad instruction, stale source, missing capability or execution error; diagnose which before changing the skill.
- **Suggested preference or routine:** keep it provisional until the person confirms it. Repeated observation alone does not create new authority or an automatic schedule.

For each accepted learning item, record its source/feedback locator, scope, prior behavior, desired behavior, affected records/skills, revision and validation. Private context stays private; examples for a generic method contribution must be independently synthetic, not lightly renamed messages or receipts.

Agree during setup how private skill maintenance should work. A practical option is to apply reversible fixes for explicit corrections and demonstrated defects, retaining history; propose inferred preference changes and changes to external-action authority before activation. Respect the user's choice and avoid repeatedly asking for already authorized routine maintenance.

## 4. Update a skill without losing what worked

1. Read the current private skill, its relevant profile/workflow record and the evidence for the change. Identify the smallest change that addresses the actual problem.
2. Preserve the prior version and record the intended effect and affected contexts. Do not replace the whole skill with the latest conversation or accumulate contradictory instructions.
3. Update the canonical profile or decision first where appropriate, then adjust the skill or its references. Check other current views that depended on the old rule. Keep unrelated user edits.
4. Replay the corrected/failed example and at least one earlier successful example from the affected scope, using permitted inputs and avoiding unauthorized external effects. Verify meaning, source support, tone or tool behavior as relevant; structural validation alone is insufficient.
5. Integrate only after the relevant checks pass. If they fail, retain the prior working version, record the unresolved candidate and repair it within scope. Changes to authority or inferred preferences still need the actual required decision.
6. Record the new version, changed files, tests, remaining uncertainty and rollback path in the private skill register. Confirm that the installed/discovered skill points to the revised version instead of leaving stale copies active.

Prefer specific improvements over universal rules derived from a single incident. Do not make an instruction stricter simply because a source contained one unusual exception. Do not silently switch model or reduce reasoning depth as an optimization.

Use the bundled [maintenance skill](../../maintain-codex-workspace/SKILL.md) as the executable method for these refresh and revision runs. Install the [everyday defaults](everyday-defaults.md) so short requests and scoped corrections trigger the right behavior without repeated instructions.

## 5. Refresh sources and reassess routines

During active work, incorporate relevant new information under the agreed source scope. For future refreshes, use an actual authorized schedule/event mechanism with source bounds, cursor/overlap, duplicate handling, notification intent and failure recovery. Reuse existing routines and do not create competing loops.

Where requested, a periodic review can examine changed responsibilities, recurring failures, stale sources, disconnected tools and skill usefulness. Ground proposed changes in observed outcomes and user feedback. Keep a list of supported jobs and actual gaps rather than claiming the workspace can already do everything.

Useful measures include whether cited context is retrievable and current, corrections stop recurring, outputs need fewer repeated edits, routines complete without duplicate actions, and interrupted work resumes from real checkpoints. State the checked period and examples; do not invent improvement scores.

## 6. Acceptance and handoff

Demonstrate a source refresh, retrieval of current project context, one authorized cross-tool workflow, a correction propagated into a skill with a regression check, and resumption from saved state. Test only the selected authorized scope, mark unavailable tools/untested workflows clearly, and retain a usable manual route when automation is not yet proven.

Show the person how to say “remember this for this project”, “change how you do this task”, “refresh my context”, “show what changed”, and “restore the previous skill version”. Resolve each request through the actual private records and applicable memory policy. Do not make them maintain the toolkit to keep their own workspace useful.
